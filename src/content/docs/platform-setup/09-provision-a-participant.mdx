Costa Frames applied through Danube Cloud's portal, which passed the application to the association's onboarding API. The association has admitted Costa, and its onboarding application has registered Costa as a holder at the issuer. The portal has read the approval. Now Danube Cloud's platform has to deliver what a new member expects within seconds: an identity, a Credential Service, a connector context, and access to a data plane.

## One request for all services

A participant exists in several services at once. The **Connector Fabric Manager** (CFM) creates, changes, and removes this runtime across all of them from one request. Its Tenant Manager accepts the request and keeps the record. Its Provision Manager runs the steps, and small agents do the work in each service.

## Two calls and a poll

The first call creates a **tenant**, the record of the organization.

```http
POST /api/tm/tenants
```

```json
{ "properties": { "name": "Costa Frames" } }
```

The second call creates a **participant profile** for that tenant and starts provisioning.

```http
POST /api/tm/tenants/{tenantId}/participant-profiles
```

```json
{
  "identifier": "did:web:identity.danube-cloud.example:costa-frames",
  "cellId": "c0a8e1f2-5b7d-4c3a-9e21-7f4d2a6b9c10",
  "dataspaceProfileIds": ["5b0e4c6e-7a53-4c1e-9d2b-1f6a3e8c2d10"],
  "vpaProperties": {
    "cfm.connector": {
      "dataspaceProfiles": ["bike-dataspace"]
    },
    "cfm.dataplane": {
      "authorization": { "type": "oauth2_token_exchange" },
      "transferTypeMappings": {
        "https://w3id.org/dspace-sig/profile/http-pull": {
          "transferType": "https://w3id.org/dspace-sig/profile/http-pull",
          "endpointType": "https://w3id.org/dspace-sig/profile/http-pull",
          "endpoint": "https://supplier-certificates.danube-cloud.example/api/v1",
          "tokenSource": "provider",
          "txRenewalSupport": false,
          "claimMappings": [
            {
              "from": "flow.claims.vc.withType('RecyclerCredential').claim('activities')",
              "to": "activities",
              "optional": true
            }
          ]
        }
      }
    }
  }
}
```

| Field | Meaning |
|---|---|
| `identifier` | The member's DID. Its host must be the identity host of the platform. Choose the last part once and never change it. |
| `dataspaceProfileIds` | The ID of the provisioning profile from lecture 7. |
| `cfm.connector` | The connector profiles under which this participant is served. |
| `cfm.dataplane` | How Siglet and the connector authenticate to each other, which application endpoint a transfer type leads to, and which verified claims go into access tokens. Lecture 10 explains the content. Without transfer type mappings the participant gets no data plane. |

The answer is `202 Accepted`. Provisioning runs in the background, so the caller polls:

```http
GET /api/tm/tenants/{tenantId}/participant-profiles/{profileId}
```

Poll until every entry in `vpas` has the state `active`, and check the field `error`. Then read the **participant context ID** from `properties`, under `cfm.vpa.state`. Every later call for Costa needs it. This path writes `costa-frames` for readability. Real IDs are generated by the platform.

Costa now has a connector context under the profile `bike-dataspace`, a key pair in the secret store, a published identity document, a Credential Service, a registered data plane, and the token exchange mappings that let the services act for it.

## The member requests its credentials

Costa has no credential yet. Provisioning creates the runtime and nothing else. The association's onboarding application has registered Costa as a holder at the issuer, so the platform never writes facts about a member there. Now the portal tells Costa's Credential Service to request its membership credential:

```http
POST /api/identity/participants/costa-frames/credentials/request
```

```json
{
  "issuerDid": "did:web:issuer.bike-dataspace.example:issuer",
  "credentials": [
    { "id": "bike-membership-v1", "type": "MembershipCredential", "format": "VC2_0_JOSE" }
  ]
}
```

The answer is `201`, with the address of the request in the `Location` header. A `GET` on that address returns its status, which moves from `CREATED` to `ISSUED`. `ERROR` usually means that a required property is missing in the holder record or that the definition ID is wrong.

The Issuer Service can also start this step by sending an offer to Costa's Credential Service, which then makes the same request.

Costa is ready when the membership credential is stored in its Credential Service. Counterparties ask for it with every request, so a member without it cannot take part. Hansen Recycling gets a second entry in the same request, for the recycler credential.

## Check, and remove

Check a new participant in three steps.

1. The identity document resolves at `https://identity.danube-cloud.example/costa-frames/did.json` and lists the Credential Service and the protocol address.
2. `GET /api/identity/participants/costa-frames/credentials` shows the membership credential.
3. A catalog request from a second participant is answered.

Removal is one call, `DELETE` on the participant profile, which runs the reverse steps in the background.

:::caution
At the time of writing the removal steps of the chart do not cover the participant's context in the Identity Hub or its token exchange mappings. Check what is left after a removal and clean it up. The identity document in particular must stop resolving.
:::

Provisioning knows nothing about credentials, so removal revokes none. Revocation is the issuer's act, and the association triggers it. Agree with the association on the order for a member that leaves: revoke first, then remove.

## Key takeaways

- The Connector Fabric Manager provisions a participant in all services from one request: create a tenant, create a participant profile, poll until every part is active.
- The participant profile names the member's DID, the profiles it is served under, and the configuration of its data plane.
- Provisioning creates the runtime only. The member's Credential Service requests its credentials from the issuer, where the onboarding application registered it.
- Verify a removal, and treat revocation as a separate act of the issuer.
