The Bike Industry Association issues the credentials of the Bike Dataspace. It has no wish to run servers. Danube Cloud operates the Issuer Service for it as part of the platform. This lecture shows what the operator configures and what happens when a member asks for a credential.

## A context of its own

The Issuer Service is part of EDC Identity Hub. The installation created one context, named `issuer`, with a signing key in the secret store and an identity document on the issuer host. A member's Credential Service finds the issuing endpoint in that document, and every verifier finds the public key there.

## Definitions

Two kinds of definitions tell the Issuer Service what it may issue. Both come from the issuer part of the profile.

An **attestation definition** says where the facts about a holder come from. Two sources exist: the properties stored with the holder's record, and a row in a database table. The Bike Dataspace uses the first.

```json
{
  "id": "bike-holder-attestation",
  "attestationType": "holder",
  "configuration": {}
}
```

A **credential definition** describes one credential type: which attested facts become which claims, and for how long the credential is valid.

```json
{
  "id": "bike-membership-v1",
  "credentialType": "MembershipCredential",
  "jsonSchemaUrl": "https://bike-dataspace.example/schema/membership-credential.json",
  "attestations": ["bike-holder-attestation"],
  "validity": 31536000,
  "mappings": [
    { "input": "id", "output": "credentialSubject.id", "required": true },
    { "input": "memberOf", "output": "credentialSubject.memberOf", "required": true },
    { "input": "agreements", "output": "credentialSubject.agreements", "required": true }
  ]
}
```

```json
{
  "id": "bike-recycler-v1",
  "credentialType": "RecyclerCredential",
  "jsonSchemaUrl": "https://bike-dataspace.example/schema/recycler-credential.json",
  "attestations": ["bike-holder-attestation"],
  "validity": 31536000,
  "mappings": [
    { "input": "id", "output": "credentialSubject.id", "required": true },
    { "input": "activities", "output": "credentialSubject.activities", "required": true }
  ]
}
```

Three details matter.

- `validity` is in seconds. The value is one year.
- A definition names no format. Every credential gets the format of the issuer, which was set at installation: `vc20-bssl/jwt`.
- A required mapping makes a credential exclusive. A holder without the property `activities` cannot be issued a recycler credential, whatever it requests. An empty list counts as present, so a member that has accepted no data sharing agreement yet still gets its membership credential.

## Holders and issuance

By default the Issuer Service issues only to holders that it knows. A **holder** is a record with the member's identifier and the properties that the association attested.

```http
POST /api/issuer/admin/participants/issuer/holders
```

```json
{
  "holderId": "did:web:identity.danube-cloud.example:hansen-recycling",
  "did": "did:web:identity.danube-cloud.example:hansen-recycling",
  "name": "Hansen Recycling",
  "properties": {
    "id": "did:web:identity.danube-cloud.example:hansen-recycling",
    "memberOf": "bike-dataspace",
    "agreements": ["battery-passport-data:1.0"],
    "activities": ["dismantling"]
  }
}
```

The association's onboarding application sends this request after its staff have approved an application. The properties are what the association confirmed: the agreements from the signed copies, the activities from the waste treatment permit. As the operator you give the onboarding application a workload identity that is limited to holders and credentials in the issuer's context. Nothing else on your platform should be able to write facts about members.

Issuance itself follows the Decentralized Claims Protocol and is asynchronous.

Both messages travel over public routes, and each side resolves the other's identifier first. The same flow therefore works for Brandt Batteries, whose Credential Service runs in its own data center.

The Credential Service renews a credential by sending a new request, seven days before it expires by default. If the holder record is still there, the renewal succeeds without anybody acting.

## Revocation and change

Every issued credential names a status list by its address. The Issuer Service publishes these lists on the public route `/statuslist`, and verifiers download them. To revoke a credential, the association's application calls:

```http
POST /api/issuer/admin/participants/issuer/credentials/{credentialId}/revoke
```

At the time of writing a credential can be revoked. Suspending it for a while is not implemented.

When an attested fact changes, for example when Hansen adds the activity `material-recovery`, the association's application updates the holder's properties and sends the member a credential offer. The member's Credential Service then requests the new credential by itself, and the application revokes the old one. The same steps apply to the membership credential when a member accepts another data sharing agreement or a new version. Lecture 11 covers how long a revocation takes to reach every verifier.

## The issuer's identifier belongs to the association

The identifier `did:web:issuer.bike-dataspace.example:issuer` is written into every credential, and into the connector profile on every platform and at every self-hosted participant. It is the trust anchor of the dataspace.

If the identifier sat under Danube Cloud's domain, the association could not change its operator without reissuing every credential and updating every participant. So the association owns the domain and points it at the platform, and the chart pins the identifier with the value from lecture 4.

The signing key is still managed on Danube Cloud's platform, like the keys of hosted members. The EDC documentation recommends an Issuer Service with its own database and secret store, while in the chart it shares both with the other services. Settle both points in the contract with the association.

## Key takeaways

- The issuer is a context of its own with an identifier, a signing key, and public endpoints for requests and status lists.
- Attestation definitions say where facts come from. Credential definitions map facts to claims and set the validity.
- The association's onboarding application registers holders with attested properties. A member's Credential Service requests and renews its credentials itself.
- The issuer's identifier is the trust anchor. Keep it on a domain that the association controls.
