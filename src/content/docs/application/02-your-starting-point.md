The team has a namespace for the supplier certificate service and a first tenant to work with: Costa Frames. Before any code runs, the team needs a short list of facts from Danube Cloud's platform team. It also needs a way to prove to the platform which workload is calling.

## What the operator gives you

| Item | Example | You use it for |
|---|---|---|
| Participant context ID | `costa-frames` | The path of every Management API call for this member |
| DID | `did:web:identity.danube-cloud.example:costa-frames` | The identity that other participants see |
| Management API | `https://danube-cloud.example/api/management/v5/participants/costa-frames` | Offers, negotiations, and transfers |
| DSP address | `https://danube-cloud.example/api/dsp/costa-frames/bike-dataspace` | The address at which counterparties reach this member's connector |
| Profile name | `bike-dataspace` | The `profile` field of catalog, contract, and transfer requests |
| Token endpoint | `https://danube-cloud.example/api/auth/token` | Exchanging the token of your workload |
| Siglet token API | `https://danube-cloud.example/api/siglet` | The access tokens of data flows |
| Event stream | A NATS JetStream stream with the subjects `events.>` | State changes of negotiations and transfers |

A **participant context** is the part of a shared connector that belongs to one member. This path writes readable IDs such as `costa-frames`. Real IDs are generated by the platform. Store them, and never derive them from a company name.

## Get a token

The supplier certificate service has no password for the Management API. It runs under a Kubernetes service account, and the platform accepts the token of that service account as proof of the workload's identity. The application exchanges this token for a short-lived access token that is valid for one participant context. The mechanism is OAuth 2.0 token exchange.

```sh
curl -X POST "https://danube-cloud.example/api/auth/token" \
  --data-urlencode "grant_type=urn:ietf:params:oauth:grant-type:token-exchange" \
  --data-urlencode "subject_token=$SERVICE_ACCOUNT_TOKEN" \
  --data-urlencode "subject_token_type=urn:ietf:params:oauth:token-type:jwt" \
  --data-urlencode "resource=costa-frames" \
  --data-urlencode "scope=management-api:assets:read" \
  --data-urlencode "audience=edcv"
```

| Parameter | Meaning |
|---|---|
| `subject_token` | The service account token of your workload |
| `resource` | The participant context you act for |
| `scope` | What the next call needs, in the form `management-api[:resource]:action` with the actions `read`, `write`, and `admin` |
| `audience` | The audience that the platform's APIs expect. The operator tells you the value. `edcv` is the default of the platform chart. |

The response contains `access_token` and `expires_in`. Send the access token as a bearer token with your API calls.

The exchange succeeds only if the operator registered your service account for that participant context. The registration lists the scopes you may request. Treat it as a ceiling, and ask for the one narrow scope that a call needs.

A multi-tenant application repeats the exchange per member. The `resource` parameter selects the tenant, and the resulting token works for that participant context only.

## The envelope of a request

Management API bodies are JSON-LD. In practice this means two fixed fields in every body:

- `@context` with the value `https://w3id.org/edc/connector/management/v2`;
- `@type` with the kind of object, for example `Asset` or `CatalogRequest`.

You do not need a JSON-LD library to write or read these bodies. The connector checks each body against a JSON schema and lists the problems when a field is missing or misspelled.

## A first call

List the assets of the participant context. On a new context the list is empty. An empty list with status `200` proves that the address, the token, and the scope are right.

```http
POST /api/management/v5/participants/costa-frames/assets/request HTTP/1.1
Host: danube-cloud.example
Authorization: Bearer <access token>
Content-Type: application/json
```

```json
{
  "@context": ["https://w3id.org/edc/connector/management/v2"],
  "@type": "QuerySpec",
  "limit": 10
}
```

| Status | Meaning |
|---|---|
| `200` | The call worked. |
| `400` | The body does not match the schema. |
| `401` | The token is missing, expired, or not accepted. |
| `403` | The token is valid and lacks the scope that this endpoint requires. |

## If you run your own connector

Brandt Batteries runs a connector for one participant. Its developers follow the same lectures with these differences.

| | Managed platform | Own connector |
|---|---|---|
| **API version, at the time of writing** | `v5` | `v4` |
| **Path** | `/v5/participants/costa-frames/assets` | `/v4/assets` |
| **Authentication** | Bearer token from the token exchange | An API key in the `X-Api-Key` header, or tokens of your own identity provider |
| **Request bodies** | The same | The same |

## Key takeaways

- The operator gives you a participant context ID, a DID, the API addresses, and the profile name of the dataspace.
- A workload exchanges its service account token for a short-lived token that is scoped to one participant context.
- Request the narrowest scope that a call needs. The operator's registration is the ceiling.
- Every Management API body carries the same `@context` and a `@type`.
- A self-hosted connector uses version 4 of the API and an API key. The request bodies are the same.
